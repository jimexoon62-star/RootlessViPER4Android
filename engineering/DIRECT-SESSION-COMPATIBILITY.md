# 4.0.7 direct session compatibility experiment

The owner's 4.0.6 HONOR capture has advancing read/write counters but zero input/output peaks and a native Spotify track with NO_MEDIA_PROJECTION. The full native ViPER engine cannot process samples it does not receive. This is not evidence that AAudio itself is incompatible or that every Spotify track is restricted.

This experimental build defaults to an explicitly labelled alternative: Android DynamicsProcessing on each eligible original audio session. It never captures, changes capture policy, suppresses original audio, creates a replacement AudioTrack or acquires audio focus. This is **not the complete ViPER native engine**. Graphic EQ and output gain are mapped to Android's EQ with automatic positive-EQ headroom and a fixed stereo-linked safety limiter. Linear phase, parametric EQ, convolver, bass, compressor, spatial and other native effects are unavailable in this mode; their controls are disabled, and their saved values remain intact.

Settings > Troubleshooting > Direct session compatibility selects the backend. Changing backend stops processing; the owner then turns power on again. Disable compatibility to retain the full existing capture engine, subject to source capture eligibility. Only one processor service may start at a time. The direct service uses the normal FOREGROUND_SERVICE_MEDIA_PLAYBACK permission; it does not require projection consent because it does not perform projection.

Session effects are keyed by session and UID, released when identities disappear/change, and quarantined after creation, update or control failure until the session disappears. Listener callbacks never re-enable effects. A once-per-second control check catches disabled effects even if listeners are missing; it establishes API control only, not audible output. Creation/update exceptions release acquired resources; teardown is idempotent and release failures are explicitly logged. The full native backend retains its existing synchronous mute-release failure recovery.

Limits: attachment to another app's session and actual routing remain OEM/API dependent. No promise is made that DynamicsProcessing implements the exact native ViPER response, that control acquisition proves audible processing, or that this resolves restricted capture for the full engine. No Honor or Bluetooth acceptance is inferred from an emulator.

Validation is in progress. Tests added: pure settings validation/headroom, lifecycle/identity changes, bounded failed attachment, update/control failures, missing callbacks, concurrent shutdown, stale callbacks and release failure reporting; Android measurement of a self-owned opt-out source at 0 dB, -12 dB, uniform -12 dB EQ and after release; real service enable/disable and backend switching. Results will be recorded after execution.

Installation: same package and repository test signing identity as 4.0.6. Install as an update without uninstalling or clearing data. Export profiles using the existing backup UI before testing. If Android rejects the update, retain the installed app and report the error; do not uninstall. To return to full native processing, turn power off, disable direct compatibility, and turn power on with legitimate projection consent. A binary downgrade can be rejected by Android; a subsequent higher-version build of the previous runtime is the data-preserving fallback.

The shutdown audit also found that a service can remain bound to MainActivity after stopSelf/stopService. Both backends now explicitly stop processing before waiting for service destruction; MainActivity detaches the stopped binder. The direct Android lifecycle test deliberately retains an extra binder and asserts that processing stops while the service instance still exists. Capture startup failures retain their bounded recovery backoff instead of immediately cancelling it with stopSelf.

The initial Android measurement run (39083469713, source 3fa756f) passed installation/startup/native/capture stages but failed the new direct gain assertion: the session Visualizer reported -1698 mB before and after the -12 dB update. AOSP Android 16 explains why that meter is unsuitable: Visualizer is INSERT_FIRST while DynamicsProcessing is INSERT_LAST, so a session meter observes pre-effect input. The corrected test measures the output mix after our self-owned session insert, in a synthetic-only emulator; the exact gain assertion is retained. No Visualizer is added to production and no Spotify audio is captured. A corrected test result is still pending.

AOSP source for ordering: https://android.googlesource.com/platform/frameworks/av/+/refs/heads/android16-release/media/libeffects/visualizer/EffectVisualizer.cpp and https://android.googlesource.com/platform/frameworks/av/+/refs/heads/android16-release/media/libeffects/dynamicsproc/EffectDynamicsProcessing.cpp .

Performance evidence from the latest owner capture: the logged block is 10,752 float samples / 43,008 bytes, or 5,376 stereo frames (112 ms at 48 kHz). Seven steady sparse DSP samples range from 6.3 to 19.7 ms, with an initial 244 ms startup sample; all eight signal peaks are zero. This does not measure unsampled stalls or end-to-end latency, but it gives no basis for increasing buffers to cure a source that supplies no captured signal. No buffer increase or sample-rate workaround is introduced.
